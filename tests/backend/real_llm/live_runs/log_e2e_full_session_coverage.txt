ASSISTANT (26.3s):
Achei a fonte oficial. O algoritmo é definido na especificação Accessible Name and Description Computation (AccName) do W3C, atualmente na versão 1.2, publicada em https://www.w3.org/TR/accname-1.2. A versão anterior (1.1) está em https://www.w3.org/TR/accname-1.1, e o W3C APG também resume o cálculo em https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions.
Como funciona o algoritmo:
O user agent constrói a string do nome acessível percorrendo uma lista de métodos potenciais de nomeação e usa o primeiro que gerar um nome. A ordem de prioridade é esta:
1. aria-labelledby — se presente e contiver pelo menos um IDREF válido, processa os IDs na ordem em que aparecem, concatenando o texto dos elementos referenciados. O algoritmo é invocado recursivamente para cada nó referenciado. Detalhe importante: se o nó já faz parte de uma travessia aria-labelledby em andamento, a referência não é seguida de novo (evita loop infinito).
2. aria-label — se o nome ainda estiver vazio, usa a string direta do atributo.
3. Associação nativa de label — para inputs, o <label> via for/id ou o elemento contido dentro do label; para tabelas, o <caption>; para fieldsets, o <legend>; para imagens, o alt.
4. Conteúdo do elemento (name from content) — para elementos que suportam nome a partir do conteúdo, como botões e links, o texto interno é usado, com recursão em cada nó filho.
5. Atributo title — usado como último recurso de fallback.
6. placeholder — só como último recurso, e nunca como única descrição de um formulário.
Um ponto normativo que vale destacar: o aria-labelledby sempre vence quando presente e válido, sobrescrevendo até o label visual nativo. E o cálculo é recursivo — quando um aria-labelledby aponta para um elemento, o algoritmo roda de novo sobre os filhos desse elemento para montar a string final.
Se quiser, posso aprofundar em algum caso específico, como o comportamento de aria-labelledby apontando para si mesmo ou para elementos ocultos, que é uma das partes mais sutis da especificação.
